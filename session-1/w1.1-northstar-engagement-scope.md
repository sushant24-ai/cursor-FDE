# W1.1 Homework — Engagement Scoping

**Bootcamp:** Cursor Partner FDE Bootcamp APJ 6 — Session 1  
**Workshop:** Workshop 1 · W1.1  
**Customer:** Northstar Logistics  
**Phase:** Phase 1 — Scaffolding gap

---

## One-liner

Northstar is high adoption, low scaffolding. Scope a **3-week Scaffolding** engagement with platform staff: Team Rules + skills/sub-agents so inconsistent gains become org standard; Bugbot / async is Phase 2 after rules exist.

---

## Customer

| Field | Detail |
|---|---|
| Industry / constraint | B2B SaaS logistics, Series C ~$80M ARR. Wants to move fast; no security/compliance in the room for Phase 1. |
| Engineering org | ~250 engineers across 30 teams. TypeScript monolith + Go services. Modern CI/CD, fast deploy cadence. |
| Current tools | Cursor live ~3 months; ~85% of engineers active. |
| Curve position + evidence | Past autocomplete / past basic IDE chat — **local agents in wide use, no org standard**. Evidence: high seat activity, “some teams flying / others barely using,” **no central rules or sub-agents**, each of ~30 teams improvising. |

**Problem in one sentence:** Real productivity gains exist, but they are uneven because there is no shared scaffolding — so the ask “level everyone up” is a Phase 1 scaffolding problem, not a license or factory problem.

---

## Engagement

| Field | Choice |
|---|---|
| **Primary pillar / type** | **Scaffolding** (rules, skills, sub-agents, hooks, settings & policies) |
| Why not enterprise readiness | Rollout already done (~85% active). |
| Why not async / cloud agents | Teams are not yet sync-proficient as an *org*; uneven practice first. |
| Why not factory / SDK | Too early; no shared baseline. |
| Why not Trust & Governance as primary | No security in the room; keep Phase 1 engineering standards only (governance is cross-cutting and light). |
| **Phase 2 (optional, week 5+)** | Bugbot / Cursor code review on the TS monolith + 1–2 highest-churn Go services (after review standards exist in rules / `BUGBOT.md`). |
| **Duration** | **3 weeks** embed + 1 week light shadow/handoff |
| **Champion** | VP of Engineering (sponsor) |
| **Daily co-builders** | Two platform staff engineers |
| **Pilot set** | 3–5 teams including flying + lagging; pull 2–3 flying leads in week 2 as pattern donors. Do **not** start with all 30 teams. |

---

## Weekly outcomes

### Week 1 — Diagnose & baseline
- Shadow 1 flying team + 1 lagging team.
- Inventory current prompts/rules (if any).
- Draft Team Rules (enforceable) + monorepo vs Go service rule split.
- Agree day-30 metric with VP Eng.

### Week 2 — Ship primitives
- Land Team Rules + project rules for TS monolith and Go services.
- Add ≥2 skills (e.g. PR review playbook, service-onboarding map) and ≥2 sub-agents (e.g. `explore-monolith`, `go-service-review`).
- One `beforeShellExecution` or `afterFileEdit` hook as a guardrail pattern (not a full compliance program).
- Pilot on 3–5 teams spanning both cohorts.

### Week 3 — Level-up & handoff
- Office hours + short playbook for remaining teams.
- Platform staff own the primitives (repo + Cursor team dashboard).
- Measure pilot teams vs baseline.
- Soft handoff; FDE on-call for questions only.

### Week 4 (light)
- Platform runs the rollout; FDE reviews metrics and scopes Phase 2 Bugbot only if Week 3 landed.

## Success metric (day 30)

| | |
|---|---|
| **Baseline (measure in Week 1)** | ~85% active is already high; the gap is **consistency**. Capture: (a) share of PRs where Cursor was used with team rules loaded, (b) self-reported “confident weekly use” by team, (c) time-to-first-useful PR for new Cursor users on lagging teams. *(Brief does not give quality numbers — Week 1 measurement task.)* |
| **Target** | Lagging cohort within ~20% of flying cohort on the agreed confidence/usage-quality metric; **100% of pilot teams** on Team Rules + documented skills/sub-agents; platform staff can add a rule without the FDE. |
| **How measured** | Cursor admin analytics + short pilot survey + proof that rules/skills live in team dashboard / repo (**not** on the FDE laptop). |

---

## Primitives left behind

| Primitive | What ships |
|---|---|
| **Rules** | Enforced Team Rules (TS + Go conventions, PR expectations, “no secrets in chat”). Repo rules for monolith and Go services. |
| **Hooks** | One project hook (e.g. ask on risky shell / format-after-edit) as the pattern; platform extends. |
| **Skills / sub-agents** | ≥2 skills, ≥2 sub-agents in a platform “Cursor standards” repo. |
| **Team vs repo** | Team Rules + marketplace skills in Cursor dashboard; repo `.cursor/` for monorepo/services. **Nothing laptop-only.** |

---

## Risks

| Risk | Mitigation |
|---|---|
| **Change management** | Flying teams resist “standardization.” Harvest *their* patterns into Team Rules; don’t invent from scratch. Lagging teams get office hours, not a PDF. |
| **Legacy / multi-stack** | Monolith + many Go services — don’t rewrite; one vertical slice of primitives both stacks can use. |
| **Compliance** | Security not in the room. No Autofix-at-scale, no broad MCP trust, no “we’re compliant” claims. Flag Privacy Mode / MCP allowlist as a Phase 1.5 conversation with security. |
| **What we will not do** | Strategic “software factory” SOW; company-wide Bugbot Autofix on day one; custom SDK; pretend 30 teams transform in 3 weeks. |
